# Known Limitations

These are documented, by-design behaviors and honest gaps — not bugs. Per the Phase 1 freeze agreement, none of these should trigger a parser change on their own; they're the context a Phase 2+ renderer (or a future parser change request) needs to design around.

## 1. Verified against exactly one sample PDF

Everything in [TEST_RESULTS.md](TEST_RESULTS.md) was checked against a single real client quotation (female, non-smoker, age 26, Class 2 occupation, Medic TotalCare Plan 200 / SmartSaver300). Every anchor string, label, and table layout the parser depends on was confirmed against that one document's actual text layer, not assumed from visual inspection alone.

**Implication:** anchors that are unique in this sample (e.g. exact section heading text, exact benefit-item label wording) are trusted to repeat across PruBSN's other AnugerahMax + Medic TotalCare quotations because the PDF is system-generated from a fixed template — but this has not been confirmed against a second real PDF yet. Before this parser is relied on for other clients, agents, or ages, run `test/run-sample.js` against 2-3 more real quotations (ideally spanning different ages, genders, and — if available — a Platinum/higher-tier plan) and treat any new failures as real bugs, not limitations.

## 2. Three benefit rows are genuinely merged cells in the source PDF

`data.benefits.benefitItems` always has 18 entries, but three of them have `value: null` with an accompanying warning:

- `Surgical Procedure and Treatment`
- `Post-Hospitalisation Treatment`
- `Outpatient Kidney Dialysis Treatment`

In the source PDF, each of these shares its actual value with an adjacent row (e.g. "Outpatient Kidney Dialysis Treatment" and "Outpatient Cancer Treatment" are one merged cell reading "RM1,000,000 per lifetime"). The parser deliberately does **not** guess and copy the neighboring value onto the empty row — see the "never invent data" rule in [ARCHITECTURE.md](ARCHITECTURE.md). A renderer must handle `value: null` gracefully (e.g. visually grouping the row with its neighbor, or omitting it) rather than printing "null" or a blank line.

**Phase 2 addendum:** a 4th row, `Intensive Care Unit (ICU) / Cardiac Care Unit (CCU)`, is not `null` but has the same underlying problem — its extracted value is only the day-count parenthetical ("(maximum 150 days per rider year)"), because the shared "As charged" token physically sits on the neighboring "In Hospital and Related Services" line, not this one. The parser's own `looksLikeValue()` warning check doesn't catch this (the day-count phrase incidentally matches its "per rider year" pattern), so it produces no warning — but the renderer's `primaryValue()` formatter correctly recognizes a bare day-count note isn't a real coverage figure and falls back to the same neutral treatment as the three `null` rows. Net effect: **treat this as 4 merged-cell rows, not 3**, when reviewing renderer output.

## 3. `options.columns[].productName` is low-confidence by construction

Reconstructing each column's product name requires splitting text that wraps across lines and, for two of the three columns, shares single physical lines — solved with a column-offset calibration technique (see `extractOptions.js`), not a guarantee. This field always carries a warning recommending manual verification, regardless of whether the reconstruction looks right. Every other field in `options.columns` (contribution, co-payment, room & board, limits) is extracted with the same confidence as the rest of the parser.

## 4. Plan-tier/annual-limit cross-check only knows about "Plan 200"

`validate.js`'s `KNOWN_PLAN_TIER_ANNUAL_LIMITS` reference table has one entry. A quotation for any other tier (e.g. a hypothetical "Plan 250" or "Plan 500") will produce a warning saying the tier is unrecognized and could not be cross-checked — it will **not** be treated as a mismatch, and extraction of that quotation's actual data is unaffected. Extend the table in `validate.js` as real quotations for other tiers are seen.

## 5. `quotationNumber` and `validUntil` are not real PDF data

Neither field exists anywhere in PruBSN's PDF. Both are generated by `parseQuotation()` (a caller-supplied or `null` quotation number; `validUntil = quotationDate + validityDays`, default 14 days). The earlier hand-made version of this quotation fabricated a quotation number that looked authoritative but wasn't — this is the intentional fix, and both fields carry a `generated: true` flag in the returned data specifically so a renderer can visually distinguish them from document facts (e.g. shown as an editable field, not printed as read-only text).

## 6. Optional fields are best-effort

`benefits.fullExclusionsList` and `benefits.waitingPeriods` were marked Optional in the approved extraction model and are implemented without the same anchor-robustness scrutiny as Required fields. They work correctly against the sample PDF but haven't been stress-tested the way the Required fields have.

## 7. `pdftotext` is a dev/test-only backend

The Node test harness extracts PDF text via the `pdftotext -layout` CLI (poppler-utils). This is explicitly not what the eventual browser-based tool will use (Phase 3 needs a `pdf.js`-based equivalent). `pdf.js` reconstructs text position differently than `pdftotext`, and while every extractor was built against `lineUtils.js` primitives that don't assume a specific backend, the exact line-wrapping and whitespace-gap behavior that several extractors depend on (e.g. the "widest gap = column boundary" and column-offset-calibration techniques in `extractOptions.js`, and the merged-cell handling in `extractBenefits.js`) should be re-verified once a real `pdf.js` backend exists, before assuming Phase 1's test results transfer unchanged.

## 8. No OCR / scanned-PDF support

The parser only works on PruBSN's system-generated, text-layer PDF. A scanned image of a quotation (no selectable text) will fail extraction entirely — every extractor will come back empty and `errors` will be full of "Required field is missing" entries. There is no fallback path for this today.

## 9. Single product line

The parser's anchors and the `BENEFIT_LABEL_DICTIONARY` in `extractBenefits.js` are specific to PruBSN AnugerahMax paired with the Medic TotalCare rider at the SmartSaver co-payment structure seen in the sample. A quotation for a different PruBSN product (e.g. a pure investment-linked plan with no medical rider, or a different medical rider like Medic BoostCare on its own) would need its own anchor/dictionary review before being trusted.
